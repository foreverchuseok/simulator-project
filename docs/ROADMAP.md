# ROADMAP — 웹 시뮬레이터 개발 순서

사용자 합의: 2026-09-17. 전체 순서와 인계 상태는 이 문서에서 관리한다. 실제 구현 계약은 각 부품 문서와 현재 코드를 따른다.

## 확정한 방향

- GitHub + Vercel 웹 배포를 유지한다. 직원 약 40~50명, 예상 동시 접속 1~2명의 현장·간단 교육 용도다.
- 직원은 같은 주소로 접속한다. APK 전환과 엔진 교체는 현재 범위에 포함하지 않는다.
- 새 부품보다 부드러운 운행, 관찰하기 쉬운 화면, 모바일 조작을 먼저 완성한다.
- 정밀 부품은 유지하되 전체 운행·부품 관찰·고장 학습에 필요한 상세 수준을 구분한다.

| 3 | 부품 디자인 보완. | 기존·추가 부품의 형상과 표현 정리, 간극·피벗·동작·성능 확인. | 대기. |

## 현재 단계 — 웹 최적화

진행 순서는 다음과 같다. 상세 실행 계획은 로컬 `PLAN.md`에 둔다.

1. 기준 측정: 기기·브라우저·해상도·시점·품질 설정을 기록하고 정지·시점 이동·운행·기존 과속 시연을 비교한다. 실제 목표 휴대폰과 성능 기준을 확정한다.
2. 로프 갱신: 운행 중 매번 생성·폐기하는 형상을 재사용하는 방향으로 개선한다. 로프 경로와 카·균형추·시브 연동을 보존한다.
3. 렌더링: 반복 부품과 재질 공유, 고정부품 묶음, 그림자 범위와 해상도 등을 측정 결과에 따라 개선한다.
4. 화면 구성: 기본 배경을 단순화하고 전체 운행·부품 관찰의 상세 수준을 구분한다. 정밀 원본과 가동부 계약을 보존한다.
5. 사용 경험: 모바일 UI·카메라 구도를 정리하고 운행·표시 속도·소리의 일관성을 검토한다.
6. 통합 확인: 실제 모바일과 PC에서 기본 운행 및 기존 안전장치 동작을 확인하고 성능 결과를 남긴다.

## 인계 상태

- 실기기 기준 확정(2026-09-18): 사용자 테스트 환경은 Galaxy Tab S7 FE / Chrome, 비교 기기는 Galaxy S22+ / Chrome이다. 기존 배포에서 S22+는 상대적으로 원활하고 S7 FE는 느림·버벅임을 보고했다. 목표 FPS 수치는 아직 합의하지 않았다.
- 그림자 캐시 구현·PC 검증(2026-09-18): `js/environment.js`의 `installShadowCache()`를 `index.html`에서 설치한다. 주 화면의 그림자 생성 부품·조명·월드 행렬·표시 상태·형상 버퍼·재질을 비교해 변화가 없으면 그림자맵을 재사용한다. 움직임·지연 로딩·단면 표시 변경은 즉시 갱신하며 과속 확대 화면은 캐시에 관여하지 않는다. 2048×2048 그림자·PCFSoft 품질과 부품 형상은 유지했다. `verify_shadow_cache.mjs`의 정지/시점 이동 재계산 0회, 변경 6종 즉시 갱신 및 강제 재계산 그림자맵과 픽셀 차이 0을 확인했다. 설치된 Live Server에서 캐시를 비운 새로고침 후에도 통과했으며 화면을 확인했다. 왕복 운행 3회와 `verify_overspeed.mjs --shadows`의 트립·RST·구출 운전 통과, 브라우저 오류 0건.
- 그림자 캐시 전후 측정: Radeon Graphics / HeadlessChrome 149 / 1280×850 / 픽셀 비율 1 / 동일 그림자·기본 시점, 각 3회. 각 실행 중앙값의 중앙값은 정지 49.9→33.3ms, 시점 이동 50→33.3ms, 운행 50→50ms다. p95는 약 50ms로 남았다. 원본 결과는 `.shot-rope-performance/shadow-before.json`, `shadow-after.json`, 그림자 검증은 `.shot-render-performance/live-shadow-cache.json`이다. 이번 개선은 정지·시점 이동에 해당하며 S7 FE 실기기 개선은 사용자 재테스트가 필요하다.
- 모바일 테스트 배포(2026-09-18): 사용자 요청으로 `dc97976`을 `origin/main`에 푸시했고 GitHub의 Vercel Production 배포 성공을 확인했다. 로컬 참고 APK·jadx·Python 캐시는 커밋에서 제외했다.
- 렌더링 추가 진단(2026-09-18): `tools/verify_render_performance.mjs shadow-grass-review --detailed`로 같은 PC·1280×850·픽셀 비율 1·기본 시점에서 그림자/풀밭/배경/지면 제외를 각 3회 측정했다. 기준 프레임 중앙값 약 49.9~50ms, 그림자 제외는 세 번 모두 약 33.3ms이며 p95는 약 50ms로 남았다. 풀밭 제외는 삼각형 1,826,005→882,005개지만 중앙값 33.5/49.9/49.9ms로 개선이 일관적이지 않았다. 브라우저 오류 0건. 결과는 로컬 `.shot-render-performance/shadow-grass-review.json`. 앱 품질 설정은 변경하지 않았으며 다음 구현은 그림자 갱신·범위 비용을 우선 확인한다. 모바일 성능은 아직 미검증이다.
- 이전 재개 메모(2026-09-18): 사용자 요청으로 렌더링 추가 개선을 재개하여 아래 2차 작업을 완료했다. 로프·레일 브라켓 완료 작업을 다시 시작하지 않는다. 당시에는 기종 미응답·미커밋 상태였으며, 이후 배포와 기기 확정은 위 기록을 따른다.
- 완료: 웹 운영 방향과 개발 순서 합의, 불필요한 검증·추출 이미지 810개 정리, 최적화 계획 작성.
- 기존 과속 검증: `node tools/verify_overspeed.mjs`로 정지·로프 파지·쐐기 상승·RST·구출 운전 통과. 모바일 성능 검증을 의미하지 않는다.
- 로프 최적화 구현: `js/elevator.js`에서 5가닥이 형상 하나를 공유하고 위치·법선 버퍼를 갱신한다. 정지 중에는 동일 위치의 버퍼 갱신을 생략한다. 경로·UV·시브 연동과 기존 미커밋 변경을 유지한다.
- PC 전후 측정(2026-09-18 저장 결과): `tools/verify_rope_performance.mjs`, Radeon Graphics / HeadlessChrome 149 / 1280×850 / 픽셀 비율 1 / 그림자 켬 / 동일 기본 시점. 준비 후 정지·시점 이동·운행을 각 3회 측정했다. 로프 갱신 중앙값 2.6→0.6ms, p95 3.1→0.8ms, 120회 갱신 중 TubeGeometry 생성 600→0개. 전체 프레임 중앙값은 약 33.3~33.4ms로 큰 변화가 없고 기본 렌더 호출은 5,284회다. 전체 60fps 달성으로 해석하지 않는다. 원본 결과는 로컬 `.shot-rope-performance/before.json`, `after.json`이다.
- 로프 회귀 검증(2026-09-18 재실행 통과): `tools/verify_wire_rope.mjs`의 25개 위치·5가닥 비교에서 최대 위치 오차 약 3.32e-9, 법선 오차 0. 인덱스·UV·경계·버퍼 재사용·정지 시 갱신 생략 통과. 왕복 운행을 포함한 보고서의 브라우저 오류는 없다. 시브 스크린샷도 확인했다. 최적화 후 과속 검증도 재실행하여 트립·RST·구출 운전 통과와 브라우저 오류 0건을 확인했다.
- 렌더링 1차(2026-09-18): `tools/verify_render_performance.mjs`로 기본·배경 제외·지면 제외·그림자 제외 비용을 분리 측정했다. `js/environment.js`의 `batchRailBracket()`은 고정 레일 브라켓만 재질별로 묶는다. 6개 설치 그룹과 위치·userData를 유지하고 GLB 원본은 수정하지 않았다. 원본 메시 이름은 묶음의 `userData.sourceRanges`에 보존한다. 브라켓 메시 186→30개, 기본 화면 렌더 호출 5,284→5,128회(약 3% 감소), 삼각형 수 동일. 같은 실행 조건의 프레임 중앙값은 전후 약 50ms여서 FPS 개선은 확인되지 않았다. 이전 로프 측정의 약 33ms와 직접 비교하지 않는다. 원본 결과는 로컬 `.shot-render-performance/before.json`, `after.json`이다.
- 렌더링 1차 검증: `node tools/verify_rail_bracket_batch.mjs` 통과. 6개 브라켓의 6,840개 삼각형을 원본과 비교하여 최대 위치 오차 1.27e-8, 법선 오차 2.29e-8 이하, UV 오차 0을 확인했다. 원본·묶음 근접 렌더의 형상·설치 부품 상대 위치가 같다. `node tools/verify_overspeed.mjs`로 단면 숨김·복귀와 과속 정지·RST·구출 운전도 통과했다. 브라우저 오류 0건.
- 렌더링 2차: 카 체대·플랫폼·난간과 승장 실 서포트·실·토가드·삼방틀의 고정 메시 796→113개. `js/environment.js`의 `batchStaticChildren()`을 `js/elevator.js`의 해당 조립 함수에서만 호출한다. 이름·userData·자식이 있는 메시, 숨김·투명 부품은 제외하고 부모 로컬 좌표로 묶는다. 개별 가동부·센서·표시기 텍스처와 부모 그룹의 이동·표시 계약을 유지한다. 기존 레일 브라켓도 삼각형 병합 계산만 공용 `mergeStaticMeshBucket()`을 사용한다.
- 렌더링 2차 전후 측정: Radeon Graphics / Chromium 149 / 1280×850 / 픽셀 비율 1 / 그림자 켬 / 동일 기본 시점, 정지·시점 이동·운행 각 3회. 기본 렌더 호출 5,128→4,445회(13.3% 감소), 삼각형 수 동일. 각 실행의 프레임 중앙값을 다시 중앙값으로 집계하면 세 시나리오 모두 약 33.3ms로 동일하다. 각 실행 p95의 중앙값은 정지 50→33.5ms, 시점 이동 50→33.4ms, 운행 50→33.5ms다. 60fps 달성이나 실제 모바일 결과를 의미하지 않는다. 원본은 로컬 `.shot-rope-performance/static-before.json`, `static-after.json`이다.
- 렌더링 2차 검증: `tools/verify_static_batches.mjs`에서 35개 조립 그룹의 원본 32,808개 삼각형과 비교했다. 위치 오차 1.32e-7 이하, 법선 오차 3.08e-8 이하, UV 오차 0, 기존 이름 있는 부품 유지. 카·승장 원본/묶음 화면도 확인했다. 왕복 운행 3회, `verify_overspeed.mjs`, `verify_interlock_field.mjs`, `verify_rail_bracket_batch.mjs` 통과. 설치된 Live Server에서 캐시를 비운 새로고침 후 기본 화면·113개 묶음·로프 5개·승장 4층·IDLE·브라우저 오류 0건을 확인했다. 로컬 결과는 `.shot-render-performance/static-geometry.json`, `static-live-server.json` 및 같은 폴더의 PNG다.
- 다음 작업: S7 FE / Chrome에서 그림자 캐시 적용 후 정지·회전·확대의 체감을 비교하고, 위 3번의 남은 반복 부품과 운행 중 렌더링 비용을 개선한 뒤 위 4번의 기본 배경 단순화·관찰 화면 구분으로 이어간다. 렌더링 단계 전체 완료는 아니다. 모바일 완료 수치 기준과 실제 모바일 조작·성능 검증은 남아 있다.
- 단계 2~4를 자동으로 시작하지 않는다. 현재 사용자 요청과 이 문서의 순서를 함께 따른다.

## 문서 운영

- `AGENTS.md`: 공통 작업 규칙과 이 문서의 진입 링크.
- `README.md`: 현재 단계 요약과 이 문서의 링크. 단계 전환 시 함께 갱신한다.
- `PLAN.md`: 현재 작업 하나의 로컬 상세 계획. Git 제외. 작업 완료 후 삭제하거나 다음 작업 계획으로 교체한다.
- 부품별 기술 문서: 실제 구현이 바뀐 부분만 갱신한다. 전체 로드맵을 복사하지 않는다.
- 인계 시 이 문서의 완료 상태·남은 문제·다음 작업을 갱신한다. 다른 PC에서 로컬 계획 없이도 현재 위치를 알 수 있어야 한다.
- 새 부품과 기능을 추가할 때도 성능 기준을 다시 확인한다. 상세 형상 추가로 최적화 성과가 사라지지 않도록 한다.
