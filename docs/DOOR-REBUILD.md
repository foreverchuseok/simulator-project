# DOOR-REBUILD — 도어 계통 재공사 기록

2026-08-17에 카문·승장문과 그 주변 부품을 화면에서 걷어내고, 부품별로 다시 올리기 위해 남긴 기록이다.
Claude Code, Google Antigravity, Cursor는 도어 작업을 시작하기 전에 이 문서와 `js/archive/doors.js`를 먼저 읽는다.

앱은 이 원본을 로드하지 않는다. `index.html`에 `js/archive/doors.js`를 추가하지 않는다.

## 현재 화면 상태

걷어낸 것:

- 카 도어 패널, 유리창, 베젤, 선단 세이프티슈, 가이드슈, 후면 리브
- 카 도어 클러치(벌림형 베인)
- 카 도어 오퍼레이터(흑색 헤더, 모터, 노란 구동 풀리, 아이들러, 타이밍 벨트, 행거)

  - 연동 풀리는 케이스 양단(`±(hcW/2 - 0.115)` ≈ ±1.295), 레일 높이
- 현장 실사 인터록 GLB — 2026-09-09 사진 5장과 `20260909_094039.mp4` 기준.

  - 스위치는 헤더 고정, 가동 걸쇠·롤러는 +X 문짝, 긴 사각 구멍 걸쇠걸이는 −X 문짝에 장착한다.
  - 투명 커버·흰 절연체·배선·보조접점·황록/연분홍 도금 판금·관통 슬롯·나선 스프링을 포함한다. 현대 로고 스티커는 만들지 않는다.
  - 아래 **현장 인터록 GLB 계약**이 이전의 JavaScript 형상·고정 포켓 설명을 대체한다.

- 승장 도어 좌·우 행거 플레이트 어셈블리 — `js/elevator.js` **`buildHangerAssembly(grp, side, cx, g)`**
  (도면 173~174p + 특허 KR200462913Y1 + 실사 211020.png, 001752.png, 001821.png). 좌·우를 두 벌로 쓰지 않고 `side` 부호로 미러한다.
  - 공통: 크로메이트 베이스판(380×160×3.5) + C레일 주행 롤러 2개 + 이탈방지 롤러 1개 + 하단 도어 체결 플랜지/M8 볼트 2세트
  - **월드 +X 패널(화면 왼쪽, `right`)**: GLB의 `InterlockBase`와 `Hook`. 상부 고정 롤러, 하부 가동 롤러, 스프링 심봉·와셔·조정 너트, 접점 절연체, 사각 턱, 삼각키 평철 링크를 포함한다.
  - ★**양단 릴레이 풀리 규격**: `ROPE_R = 0.022`, `PUL_R = 0.030`.
    **풀리 홈 반지름이 상·하 가닥 간격(2·ROPE_R = 44mm)을 정하는 단일 원본이다.**
    행거판은 높이 160mm·중심 `caseCY-40mm` 라 윗변이 `caseCY+40mm` 다. `ROPE_R` 이 40mm 면
    상부 가닥이 윗변에 정확히 올라타 판 밖으로 튀어나오고, 플랜지 46mm 는 C레일 상·하 립(±38mm)을 뚫는다.
    22mm 로 줄여야 두 가닥이 판 높이 **안쪽**으로 들어와 판이 앞을 가릴 수 있다(사용자 지시 2026-08-25).
  - ★**연동 로프 Z 는 상·하 분리하지 않는다 — 한 평면 `ROPE_PLANE_Z = HP_PLATE_Z + 0.012`**:
    - 상·하 가닥 모두 **행거판 뒤 12mm**. "Z 를 나눠서 하부만 숨긴다"가 아니라 **판이 앞을 막는다**가 규약이다.
    - 12mm 는 `판 반두께 1.75mm + 풀리 반두께 11mm` 에서 나온다. 8mm 로 잡으면 활짝 열렸을 때
      행거판 바깥변이 풀리를 덮는데도 풀리 앞 플랜지가 판 앞면을 1.25mm 뚫고 나온다.
    - 로프 본선이 보이는 곳은 **행거판 사이·바깥의 열린 헤더 구간**이다.
      −X 판에서는 가운데 풀리창·좌우 고정 구멍으로만 본선이 롤러를 타고 **판 앞(승강로 쪽)** 으로
      나와 스프링 고정대에 물린다. 솔리드 금속면 앞을 본선이 가로지르면 안 된다.
  - **월드 −X 패널(화면 오른쪽, `left` 그룹) = 수놈 핀측**:
    - ★**행거판 타공창 3개** (설치도면·실사 202356, 2026-08-31):
      - **가운데 풀리창** ≈ 42 × 52mm — 중심 `RB_OFF`. 2열 홈 롤러가 창 안에 앉는다.
      - **오른쪽 고정 구멍** — `TP_ROD_X`. 상단 홈에서 나온 로프가 판 앞 스프링 고정대에 물린다.
      - **왼쪽 고정 구멍** — `TP_SPR_X`. 하단 홈에서 나온 로프가 판 앞 스프링 고정대에 물린다.
      - ★**창 좌표는 `TP_*` 텐셔너 제원에서 파생시킨다.**
      - 상부 가닥은 창 윗변보다 위라 **창으로 드러나지 않는다**.
    - **연동 로프 텐셔너 어셈블리 (실사 202356.png, 설치도면, 사용자 마킹 2026-08-31)**:
      - **중앙**: 가로로 누운 2열 홈 수평 풀리(수직축). 창 두께에 앉아 뒤=본선면, 앞=판 앞.
      - **상단 홈**: 안쪽에서 들어와 홈 원주를 감아(정면에서 와이어가 홈을 덮음) 오른쪽 고정대.
      - **하단 홈**: 안쪽에서 들어와 홈 원주를 감아 왼쪽 고정대.
      - 양쪽 고정대는 판 **앞**(승강로에서 보이는 면) L브라켓 + 전산볼트 + 압축 스프링 + 더블 너트.
    - GLB `Keeper`의 보조접점 핀 2개가 고정 스위치 측 소켓 구멍으로 들어간다.
    - 긴 걸쇠걸이는 반대편 문짝의 연장판에 체결되며, 닫힐 때 가동 걸쇠의 사각 턱을 받는다.
  - 헤더 좌표 `caseCY`·`plateZ`·`trackCtrZ`만 JS에서 전달하고 인터록 세부 제원은 GLB extras에서 읽는다.
  - 전 층 `hatchDoors[i].left` 및 `hatchDoors[i].right` 그룹에 마운트되어 도어 개폐 FSM과 동기 이동

- 승장 도어 연동(릴레이팅) 로프 — `createHangerCaseAssembly()` + `spinDoorDrive()` (실사 2026-08-18 000500·000627·000712)
  - **원리**: 로프가 안쪽에서 양단 풀리 홈을 타고 180° 감겨 밖으로 나온 뒤, 상·하 가닥이 각각 한쪽
    행거판에 고정된다. 상부 가닥에 월드 +X 판, 하부 가닥에 월드 −X 판이 물리므로 한쪽이 +X 로
    가면 반대쪽은 같은 양만큼 −X 로 끌려간다. 그래서 두 문짝이 **엉키지 않고 항상 대칭 개폐**된다.
  - **화면 오른쪽(월드 −X) = 롤러 텐셔너**: 하부 본선이 2열 홈 롤러를 타고 판 앞(승강로 쪽)으로
    나와 좌·우 스프링 고정대에 물린다. 상단 홈→오른쪽, 하단 홈→왼쪽.
  - **화면 왼쪽(월드 +X) = 상부 가닥 스프링 고정단**: 로프 끝이 인장 코일 스프링을 거쳐 물린다.
  - 형상: 상·하 가닥은 각각 고정단에서 끊긴 **마디 2개씩(총 4개)** + 양단 180° 감김 토러스 2개.
    `spinDoorDrive(h)` 가 도어 행정만 보고 마디 길이와 풀리 회전각(`Δx / ROPE_R`)을 역산한다.
    ★로프 총길이는 항상 `pulRX - pulLX` 로 보존된다 — 검증 시 `upL+upR+2*aHalf` 가 span 과 같은지 본다.
  - ★**Z 레이어**: 본선 `ROPE_Z = HP_PLATE_Z + 0.012` — 본선은 행거판 **뒤**다 (2026-08-25).
    −X 판 텐셔너만 롤러를 타고 판 **앞**으로 나와 고정된다 (2026-08-31, 설치도면·실사 202356).
    행거판 돌출물(2열 롤러 `z-0.010`, 하단 긴 연동 바 `z-0.014`, −X판 L브라켓 `z-0.012`)은
    모두 판 앞이므로 본선과 겹치지 않는다.
  - ★**본선 마디 끝점은 풀리 뒤 접선이다.** 하부 가닥은 `left ± 0.190`(행거판 좌·우 끝단)이 아니라
    `bL = RB_OFF`(풀리 뒤 접선) / `bR = RB_OFF + 0.002`
    에서 끊는다. 판 앞 스프링 고정대까지 본선을 끌면 롤러를 안 쓰고 판을 가로지른다.
  - ★**하부 두 마디의 Y·Z 에 절대 오프셋을 주지 마라.** 텐셔너가 2열 홈이라고
    `setRopeSpan(..., k.loY ± 0.004, ...)` 처럼 손대면 2.6m 스팬 전체가 어긋나 **양단 풀리
    (홈 하나짜리 수직면 풀리) 홈에서 로프가 벗어난다.** 상단홈↔하단홈 높이차와 판 앞 탈출은
    행거판 고정 튜브가 흡수한다. `verify_relay_rope.mjs` (6)번 항목이 이 회귀를 잡는다.
  - **+X 솔리드 판의 상부 클램프**: 로프가 판 뒤라서 클램프 블록도 판 뒤다.
    판 앞에는 좌면 패드와 조임 볼트 머리 2개만 나온다 — 실사에서 솔리드 판에 보이는 것도 이것뿐이다.
  - ⚠️ 카 도어 클러치를 다시 올릴 때: 클러치 베인(`z≈-0.030`)은 로프면(`z=-0.0085`)보다 앞이라
    Y 가 겹쳐도 로프를 뚫지 않는다. 베인을 로프면 뒤로 밀 때만 `caseCY ± 22mm` 를 피하면 된다.

## 행거 케이스 계약 (에이전트 필수)

사용자 영상(2026-08-17 183216) 음성이 이 구간의 원본이다. 도면 173~174p와 같다. 코드를 손대기 전에 아래를 따른다.

구조 한 줄:

**벽 앙카 L브라켓(양 끝) → C형 행거 케이스(레일).** 행거판·롤러는 문짝과 같이 올린다. 그때 롤러는 C 궤도 안으로 들어간다.

인터록 스위치 박스는 C레일 앞 고정이다. 노란 GLB 판을 공중에 띄우지 않는다.

헤더 전폭은 **고정 상수가 아니라 도어 행정에서 파생**된다(`hcW = 2*(ox + HP_W/2 + 0.075)` ≈ 2.82m).
활짝 열린 행거판이 레일 위에 남아야 하고 연동로프 고정단이 양단 풀리 안쪽에 있어야 하기 때문이다.
헤더가 삼방틀(1.82m)보다 훨씬 넓게 벽 속으로 뻗는 것은 2짝 중앙개폐에서 정상이다. 좁히지 않는다.

| 맞는 것 | 틀린 것 |
|---|---|
| 브라켓이 헤더 **양 끝단**에 있다 (개구부 바깥, 잠 기둥 쪽) | 개구부 한가운데만 보고 브라켓이 없다고 판단 |
| L브라켓이 승강로 벽과 C웹 사이 간극을 채운다 | C레일만 두고 벽과 떨어진 채 떠 있게 둔다 |
| 지금 화면에는 행거판·롤러가 없다 | 문짝 없이 판 2장·롤러를 C레일에 미리 달아 둔다 |
| 주행 롤러는 C 궤도 `z=0` 안에 건다 | 롤러를 레일 옆·앞에 따로 한 쌍 더 둔다 |
| 연동로프 **본선**은 행거판 **뒤**에서 달린다. −X 판만 롤러를 타고 판 **앞**으로 나와 좌·우 스프링 고정대에 물린다 | 본선을 솔리드 금속면 앞으로 가로지르거나, 롤러를 안 쓰고 고정대에 바로 묶거나, 고정대를 판 뒤에 숨긴다 |
| 상·하 가닥 간격은 `2·ROPE_R`(44mm)로 행거판 높이 **안쪽**이다 | `ROPE_R` 을 키워 상부 가닥이 판 윗변 위로 올라타게 둔다 |
| 커버 안에 **ㅓ자 흰 하우징**이 보인다. 중간 볼트 2개, 끝 단자 2+2 가로 일렬, 노란 전선, 돼지발 돌출 | 투명 껍데기만 두고 내부를 빼거나, 단자를 위아래로 세운다 |

하지 말 것:

- `models/gltf/hall_interlock.glb`를 `buildHatchDoors()`에서 다시 로드하지 않는다. 파일은 유지한다.
- 도면 등각투영의 별도 프레임 세트·덮개를 이번에 만들지 않는다.
- 벽 쪽에만 넓은 백플레이트를 두고 C레일과 레일 높이에서 연결하지 않는 고정을 만들지 않는다.
- 브라켓을 트랜섬 높이(레일보다 위)에만 두지 않는다. 브라켓 Y는 C레일 중심(`caseCY`)이다.

검증:

- Live Server 하드 리프레시 후 `?doorcam=1` 로 **헤더 양 끝**을 본다. 가운데만 보면 브라켓·연동 풀리가 안 보인다.
- 노란 인터록 판이 공중에 있으면 잘못된 상태다.
- 문을 열어 본다. 행거판이 레일 끝을 벗어나거나 연동로프 고정단이 풀리를 넘어가면 `hcW` 파생이 깨진 것이다.
- 로프 길이 보존 검증 (콘솔):
  `k=hatchDoors[1].link; k.seg.upL.scale.y + k.seg.upR.scale.y + 2*k.aHalf` 가
  닫힘·열림 어느 위치에서도 `k.pulRX - k.pulLX`(2.59) 와 같아야 한다.
  하부 가닥은 고정단이 비대칭이라 `loL.scale.y + loR.scale.y + (k.bR - k.bL)` 로 본다.
- 로프 가시성 규약 자동 검증: `python -m http.server 8777` 띄우고
  `node tools/verify_relay_rope.mjs 8777`. 닫힘·열림 양쪽에서 12개 항목이 다 PASS 여야 한다.
  (로프면이 판 뒤인지, 두 가닥이 판 높이·타공창 안인지, 마디가 겹치지 않는지, 끝점이 고정단과 맞는지)
- 그림 검증: `node tools/shot_relay_rope.mjs 8777` → `.shot-relay/relay_*.png`.
  ★활짝 열린 상태의 헤더 **양 끝단**을 반드시 본다. 이때 행거판이 풀리를 덮는데,
  로프면이 얕으면 풀리 앞 플랜지만 판을 뚫고 나온다 — 닫힘 화면만 보면 절대 안 잡힌다.

## 현장 인터록 GLB 계약 (2026-09-09)

사용자가 제공한 사진 `20260909_093846/093942/093943/094011/094013.jpg` 및 영상 `20260909_094039.mp4`가 외형·부착 관계의 기준이다. 영상 6~8초에서 반대 문짝의 긴 걸쇠걸이와 헤더에 남는 스위치를 확인할 수 있다. 이전의 고정 16mm 포켓 블록은 사용하지 않는다.

| GLB 노드 | 부착·동작 |
|---|---|
| `SwitchAssembly` | 헤더 고정 스위치·투명 커버·받침판·고정 접점. |
| `InterlockBase` | +X 문짝의 장착판·상부 고정 롤러·스프링 가이드. |
| `Hook` | +X 문짝의 가동 걸쇠·하부 롤러·흰 접점부. 피벗을 중심으로 회전. |
| `Keeper` | −X 문짝의 긴 걸쇠걸이·사각 관통 구멍·보조접점. |
| `Spring` / `SpringSeat` / `SpringBottomWasher` | 단일 나선 코일. 심봉 축을 유지하며 레버 높이에 따라 압축. |
| `LinkStock` / `LinkFoot` / `LinkPin` | 일정 길이의 평철과 하부 캠 핀 장공. |

- `T(x,y,z)=(x,-z,y)`, 미터 단위, glTF Y-up, scale=1. GLB X는 완전 닫힘 어셈블리의 X, Y는 트랙 중심 기준, Z는 행거판 중심 기준이다.
- 래퍼: 헤더 `FieldInterlockFixed`, +X 문짝 `FieldInterlockMoving`, −X 문짝 `FieldInterlockOpposite`. 문짝 래퍼의 X에는 닫힘 중심값의 반대 부호를 적용한다.
- `InterlockRoot.userData.contractVersion=2`. `latch`·`spring`·`link` extras가 치수와 애니메이션의 단일 원본이다. JS에 각도·피벗을 중복 입력하지 않는다.
- 가동 사각 턱 폭 6mm, 네모 입구 아래 물림 8mm, 해정 후 간극 4mm, 개방측 여유 4.5mm, 착석측 0.5mm를 모델 기준값으로 유지한다. 평철 걸쇠걸이는 3mm 두께, 구멍 Z 폭 7mm, 가동판 두께 4mm이다.
- 정확한 회전 변환으로 12mm 리프트를 푼 해정각은 약 0.114192rad(6.54°). `h.latch.liftRad`는 내보낸 GLB에서 읽는다.
- `hallLatchPocket`은 반대 문짝의 구멍 입구, `hallLatchKeeperLip`은 가동 턱 하단 마커다. 월드 좌표로 물림을 재며 회전한 판의 AABB로 대신하지 않는다.
- `HallInterlock.updateAll()`은 스프링과 링크의 변환만 갱신한다. 렌더 루프에서 메시·재질·기하를 생성하지 않는다. GLB는 한 번 로드하고 층별 메시 기하·재질은 공유한다.
- 사진에는 치수 기준자가 없으므로 외형·두께·색상은 교육용 재구성이다. 위 수치를 실제 제품의 설치·검사 허용값으로 해석하지 않는다. 카·도어 치수 `const S`는 변경하지 않았다.

검증:

- `node tools/verify_interlock_field.mjs`: 자체 로컬 서버에서 4개 층의 물림·해정, 관통 구멍, 스프링 압축, 평철 길이, 문짝 부착 관계, 개방 행정의 간섭, 삼각키·복귀와 화면을 확인한다. CDN 접근이 필요하다.
- `blender/scripts/render_hall_interlock.py`: 내보낸 GLB를 다시 읽어 Blender 정면·해정 렌더를 확인한다.
- 산출물은 `.shot-interlock-field/`. 로컬 참고 영상 프레임은 `.shot-interlock-ref/`에 두며 앱에서 로드하거나 Git에 올리지 않는다.
- 승강로 −Z에서 보면 화면 왼쪽은 월드 +X, 화면 오른쪽은 월드 −X이다. 사진에 맞춘다고 좌우 부호를 뒤집지 않는다.

## 부품을 다시 올릴 때

1. 이 문서와 `js/archive/doors.js`에서 해당 구간만 읽는다.
2. `js/elevator.js`의 스텁 `buildCarDoors()` 또는 `buildHatchDoors()`에 그 구간만 넣는다.
3. 요청하지 않은 다른 도어 부품을 한꺼번에 복원하지 않는다.
4. 과거 형태를 참고하되, 사용자가 새 자료를 주면 새 자료가 우선이다.
5. 스티커 PNG와 `const S` 도어 치수는 확인 없이 바꾸지 않는다.
6. `index.html`에 아카이브 파일을 연결하지 않는다.

운행 계약(복원 전까지 스텁이 지킨다):

- `carDoorL` / `carDoorR` 과 `hatchDoors[i].left` / `.right`
- `userData.cx`, `userData.ox`
- `spinDoorDrive(h)` — **더 이상 no-op 이 아니다.** 승장 연동로프 마디·양단 풀리 회전·폐문 스프링 길이를
  `h.link` 핸들로 갱신한다. `h.link` 가 없으면 즉시 return 하므로 카 오퍼레이터 복원 시에도 안전하다.
  `ui.js` 의 `openDoors()`/`closeDoors()` 에서 **승장 행거판(`h.right`) 트윈의 `onUpdate`/`onComplete`** 로
  호출한다. ★카도어 트윈에만 물리면 한 프레임 밀려서 로프 끝이 고정단에서 어긋난 채 멈춘다.
- `h.hook`, `h.triKey`, `h.doorWeight`, `h.relPulley` 는 없어도 `ui.js`가 통과한다
